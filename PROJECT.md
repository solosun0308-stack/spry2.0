# PROJECT.md: Spry

This file describes the structure of the `spry` monorepo: folders, what lives in each, and the contracts between the parts. It contains no implementation code. It is the source of truth that code is generated from.

## 1. Scope of the first slice

- Backend exposes `GET /api/meetings` (list) and `POST /api/meetings` (create one).
- A meeting has: `id`, `title`, `starts_at`, `ends_at`, `attendee_count`.
- Frontend has one page: a list of meetings and a form that adds a new one.

Out of scope: authentication, caching, queues, background jobs, reverse proxy, orchestration manifests, any endpoint not listed above.

### What each folder is for

- `backend/`: the HTTP API and everything it needs. Owns the database schema through its models and migrations.
- `backend/app/`: application code. `routers/` holds endpoint handlers, `models.py` the database tables, `schemas.py` the API shapes.
- `backend/alembic/`: Alembic environment and migration scripts. The only way the schema changes.
- `frontend/`: the web client. Talks to the backend only through `src/api.ts`.
- `frontend/src/components/ui/`: shadcn/ui components, generated by the shadcn CLI.
- `docs/`: written decisions and documentation. No code.
- Root: `docker-compose.yml` (runs everything locally), `.env.example` (documents every environment variable), `PROJECT.md` (this file).

## 4. Docker Compose services

`docker compose up` is the only command a new developer runs after installing Docker Desktop. All variables have defaults, so no `.env` file is required.

### postgres
- Image: `postgres:16`
- Port: 5432 (published to host as 5432)
- Depends on: nothing
- Readiness: healthcheck `pg_isready -U $POSTGRES_USER -d $POSTGRES_DB`, interval 5s, retries 10
- Data: named volume `spry_pgdata`

### backend
- Build: `./backend`
- Port: 8000 (published as 8000)
- Depends on: `postgres` with `condition: service_healthy`
- Readiness: healthcheck performs an HTTP GET to `http://localhost:8000/api/meetings` using the Python standard library (the image has no curl), expecting status 200. Interval 5s, retries 10.
- Environment: `DATABASE_URL`, `CORS_ORIGINS`

### frontend
- Build: `./frontend`
- Port: 5173 (published as 5173), Vite dev server bound to `0.0.0.0`
- Depends on: `backend` with `condition: service_healthy`
- Readiness: none required; nothing depends on it
- Environment: `VITE_API_URL`

Startup order is therefore: postgres, then backend, then frontend.

## 5. Contracts between parts

### 5.1 API contract

Base path: `/api`. Content type: `application/json`.

**Meeting object**

| Field | Type | Notes |
|---|---|---|
| `id` | integer | assigned by the server |
| `title` | string | 1 to 200 characters, not blank |
| `starts_at` | string | ISO 8601 date-time with timezone offset, e.g. `2026-10-05T09:00:00Z` |
| `ends_at` | string | ISO 8601 date-time with timezone offset |
| `attendee_count` | integer | 0 or greater |

Responses always return datetimes in UTC (`Z`).

**`GET /api/meetings`**
- Response `200`: JSON array of meeting objects, ordered by `starts_at` ascending, then `id` ascending. An empty table returns `[]`.
- No pagination, no filtering.

**`POST /api/meetings`**
- Request body: `title`, `starts_at`, `ends_at`, `attendee_count` (all required; `id` is not accepted).
- Response `201`: the created meeting object, including `id`.
- Response `422`: validation failure, using FastAPI's standard error body.

**Validation rules**
- `title` is required, non-blank, at most 200 characters.
- `starts_at` and `ends_at` must include a timezone.
- `ends_at` must not be before `starts_at` (equal is allowed). Violation returns `422`.
- `attendee_count` must be an integer >= 0.

### 5.2 Database contract

- Table `meetings`: `id` (integer, primary key, auto-increment), `title` (varchar 200, not null), `starts_at` (timestamptz, not null), `ends_at` (timestamptz, not null), `attendee_count` (integer, not null).
- Database-level check constraints: `ends_at >= starts_at` and `attendee_count >= 0`.
- Defined once in `backend/app/models.py` and created only by an Alembic migration.

### 5.3 How the frontend finds the backend

- The frontend reads the backend base URL from the environment variable `VITE_API_URL` (e.g. `http://localhost:8000`).
- `VITE_API_URL` is read in exactly one place, `frontend/src/api.ts`. No URL is hardcoded anywhere else.
- The URL is used by the browser, so in Compose it is `http://localhost:8000`, not the internal service name.
- For deployment, changing this one variable is the only change needed to point the frontend at a different backend.

### 5.4 CORS

- Configured in `backend/app/main.py` from the environment variable `CORS_ORIGINS`, a comma-separated list of allowed origins.
- Default: `http://localhost:5173`.
- Allowed methods: `GET`, `POST`, `OPTIONS`. Allowed headers: `Content-Type`. Credentials: not allowed. Wildcard origins are not used.

### 5.5 Migrations

- Run by the backend container itself, automatically, on every start: `entrypoint.sh` runs `alembic upgrade head` and then starts Uvicorn.
- This is safe because the backend only starts after postgres reports healthy.
- Nobody runs migrations by hand. Developers create new migrations with `alembic revision --autogenerate` inside the backend container and commit the generated file.
- Alembic reads `DATABASE_URL` from the environment, the same variable the application uses.

## 6. Environment variables

Documented in `.env.example`, all with local defaults.

|---|---|---|
| `POSTGRES_USER` | postgres | `spry` |

## 7. Definition of done for this slice

1. On a clean clone, `docker compose up` brings up all three services with no further steps.
2. `http://localhost:5173` shows the meetings list (empty at first).
3. Submitting the form creates a meeting and it appears in the list.
4. Submitting a meeting with `ends_at` before `starts_at` is rejected with `422`.
