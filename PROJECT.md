# PROJECT.md: Spry

This file describes the structure of the `spry` monorepo: folders, what lives in each, and the contracts between the parts. It contains no implementation code. It is the specification that all code is generated from.

## 1. Scope of the first slice

- Backend exposes `GET /api/meetings` (list) and `POST /api/meetings` (create one).
- A meeting has: `id`, `title`, `starts_at`, `ends_at`, `attendee_count`.
- Frontend has one page: a list of meetings and a form that adds a new one.

Out of scope: authentication, caching, queues, background jobs, reverse proxy, a second database, orchestration manifests, any endpoint not listed above.

### What each folder and file is for

**Root**
- `docker-compose.yml`: runs postgres, backend and frontend together locally. All configuration values have defaults inside this file.
- `PROJECT.md`: this specification.
- `.gitignore`: keeps `node_modules/`, `__pycache__/`, `.venv/`, `dist/` and local env files out of git.

**`backend/`**: the HTTP API and everything it needs. Owns the database schema through its models and migrations.
- `app/`: application code.
  - `main.py`: creates the FastAPI app, configures CORS, registers the router.
  - `config.py`: reads environment variables (`DATABASE_URL`, `CORS_ORIGINS`).
  - `db.py`: database engine and session setup.
  - `models.py`: SQLAlchemy table definitions. Single source of truth for the schema.
  - `schemas.py`: Pydantic request and response shapes. Single source of truth for the API contract.
  - `routers/`: one file per resource.
    - `meetings.py`: the two `/api/meetings` endpoints.
- `alembic/`: Alembic environment. `versions/` holds the migration scripts, the only way the schema changes.
- `alembic.ini`: Alembic configuration; the database URL is taken from the environment, not from this file.
- `entrypoint.sh`: container start script. Runs migrations, then starts the server.
- `requirements.txt`: exact Python dependency pins.
- `Dockerfile`: builds the backend image from `python:3.12-slim`.

**`frontend/`**: the web client. Talks to the backend only through `src/api.ts`.
- `src/`: application code.
  - `main.tsx`: mounts the React app.
  - `App.tsx`: the single page; composes the list and the form.
  - `api.ts`: the only file that calls the backend and the only file that reads `VITE_API_URL`.
  - `components/`: React components.
    - `ui/`: shadcn/ui components, generated by the shadcn CLI. Not edited by hand.
    - `MeetingList.tsx`: renders the list of meetings.
    - `MeetingForm.tsx`: the form that creates a meeting.
- `index.html`: Vite entry page.
- `package.json`: exact JavaScript dependency pins and scripts.
- `vite.config.ts`: Vite configuration (dev server host and port).
- `tailwind.config.ts`: Tailwind configuration.
- `Dockerfile`: builds the frontend image from `node:22-alpine`.

**`docs/`**: written documentation, no code.
- `decisions/0001-monorepo.md`: the decision to use one repository, with reasons and trade-offs.

## 4. Docker Compose services

`docker compose up` is the only command a new developer runs, after installing Docker Desktop. No `.env` file is needed; every value has a default in `docker-compose.yml`.

### postgres
- Image: `postgres:16`
- Port: 5432, internal to the Compose network only (not published to the host).
- Depends on: nothing.
- Readiness: healthcheck `pg_isready -U spry -d spry`, interval 5s, timeout 3s, retries 10.
- Data: named volume `spry_pgdata`.

### backend
- Build: `./backend` (`python:3.12-slim`)
- Port: 8000, published to the host as 8000.
- Depends on: `postgres` with `condition: service_healthy`.
- Readiness: healthcheck performs an HTTP GET to `http://localhost:8000/api/meetings` using the Python standard library (the image has no curl) and expects status 200. Interval 5s, timeout 3s, retries 10, `start_period` 15s (migrations run before the server starts).
- Environment: `DATABASE_URL`, `CORS_ORIGINS`.

### frontend
- Build: `./frontend` (`node:22-alpine`)
- Port: 5173, published to the host as 5173. Vite dev server bound to `0.0.0.0`.
- Depends on: `backend` with `condition: service_healthy`.
- Readiness: none; nothing depends on it.
- Environment: `VITE_API_URL`.

Startup order: postgres, then backend, then frontend. Each step waits for the previous service's healthcheck to pass.

## 5. Contracts between parts

### 5.1 API contract

Base path: `/api`. Content type: `application/json`.

**Meeting object**

| Field | Type | Notes |
|---|---|---|
| `id` | integer | assigned by the server |
| `title` | string | 1 to 200 characters, not blank |
| `starts_at` | string | ISO 8601 date-time with timezone |
| `ends_at` | string | ISO 8601 date-time with timezone |
| `attendee_count` | integer | 0 or greater |

Responses always return datetimes in UTC with a `Z` suffix.

Example meeting object:

```json
{
  "id": 1,
  "title": "Sprint planning",
  "starts_at": "2026-10-05T09:00:00Z",
  "ends_at": "2026-10-05T10:00:00Z",
  "attendee_count": 6
}
```

**`GET /api/meetings`**
- Response `200`: JSON array of meeting objects, ordered by `starts_at` ascending, then `id` ascending. An empty table returns `[]`.
- No pagination, no filtering.

Example response:

```json
[
  {
    "id": 1,
    "title": "Sprint planning",
    "starts_at": "2026-10-05T09:00:00Z",
    "ends_at": "2026-10-05T10:00:00Z",
    "attendee_count": 6
  }
]
```

**`POST /api/meetings`**
- Request body: `title`, `starts_at`, `ends_at`, `attendee_count`. All required. `id` is not accepted.
- Response `201`: the created meeting object, including `id`.
- Response `422`: validation failure, using FastAPI's standard error body.

Example request body:

```json
{
  "title": "Sprint planning",
  "starts_at": "2026-10-05T09:00:00Z",
  "ends_at": "2026-10-05T10:00:00Z",
  "attendee_count": 6
}
```

**Validation rules**
- `title` is required, non-blank, at most 200 characters.
- `starts_at` and `ends_at` must include a timezone.
- `ends_at` must not be before `starts_at` (equal is allowed). A violation returns `422`.
- `attendee_count` must be an integer >= 0.

### 5.2 Database contract

- Table `meetings`: `id` (integer, primary key, auto-increment), `title` (varchar 200, not null), `starts_at` (timestamptz, not null), `ends_at` (timestamptz, not null), `attendee_count` (integer, not null).
- Database check constraints: `ends_at >= starts_at` and `attendee_count >= 0`.
- Defined once in `backend/app/models.py` and created only by an Alembic migration.

### 5.3 How the frontend finds the backend

- The backend base URL comes from the environment variable `VITE_API_URL`.
- It is read in exactly one place, `frontend/src/api.ts`. No URL is hardcoded anywhere else.
- The URL is used by the browser, so in Compose it is `http://localhost:8000`, not the internal service name.
- To point the frontend at a different backend (for example in deployment), only this variable changes.

### 5.4 CORS

- Configured in `backend/app/main.py` from the environment variable `CORS_ORIGINS`, a comma-separated list of allowed origins.
- Default: `http://localhost:5173`.
- Allowed methods: `GET`, `POST`, `OPTIONS`. Allowed headers: `Content-Type`. Credentials: not allowed. Wildcard origins are not used.

### 5.5 Migrations

- Run by the backend container itself, automatically, on every start: `entrypoint.sh` runs `alembic upgrade head`, then starts Uvicorn.
- This is safe because the backend only starts after postgres reports healthy.
- Nobody runs migrations by hand. A developer creates a new migration with `alembic revision --autogenerate` inside the backend container and commits the generated file.
- Alembic reads `DATABASE_URL` from the environment, the same variable the application uses.

## 6. Environment variables

Defaults live in `docker-compose.yml`.

| Variable | Used by | Default |
|---|---|---|
| `POSTGRES_USER` | postgres | `spry` |
| `POSTGRES_PASSWORD` | postgres | `spry` |
| `POSTGRES_DB` | postgres | `spry` |
| `DATABASE_URL` | backend | `postgresql+psycopg://spry:spry@postgres:5432/spry` |
| `CORS_ORIGINS` | backend | `http://localhost:5173` |
| `VITE_API_URL` | frontend | `http://localhost:8000` |
